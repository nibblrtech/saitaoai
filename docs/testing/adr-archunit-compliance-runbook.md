# ADR Test Maintenance Runbook

## Purpose

This runbook documents the ADR-to-test automation system for this repository.

It covers:

1. Workflow behavior and trigger rules.
2. Marker storage and synchronization contract.
3. Supported constraint template test types.
4. Operations, governance, and troubleshooting.

## File Inventory

### Required control files

1. .github/workflows/adr-archunit-test-generation.yml
   - Primary ADR automation workflow.
   - Triggered by docs/decisions changes on push to main/master and pull_request to main/master.
   - Also supports workflow_dispatch.
   - Runs generation, deterministic sync, deterministic verify, and npm test.

2. .github/workflows/node.js.yml
   - General Node CI workflow.
   - Triggered on push and pull_request, with docs/decisions path-ignore.
   - Includes an explicit docs/decisions change detector job to skip the build when ADR files changed in mixed commits.

3. scripts/sync-adr-constraint-tests.mjs
   - Deterministic writer for compliance-generated test files.
   - Writes tests/<decision>.compliance.test.ts based on mapping rules.

4. scripts/verify-adr-constraint-coverage.mjs
   - Deterministic coverage verifier for ADR_CONSTRAINT markers.
   - Fails on missing mapped coverage or truly stale markers.

5. docs/testing/adr-constraint-to-test-mapping.md
   - Mapping rule library.
   - Supports env override via ADR_CONSTRAINT_MAPPING_JSON.

6. docs/decisions/
   - ADR source corpus.
   - Constraints are parsed from section header: Compliance Constraints.

### Generated artifacts

1. tests/<decision>.test.ts
   - ArchUnit-style architecture constraints.

2. tests/<decision>.compliance.test.ts
   - Non-ArchUnit compliance constraints generated by sync script.

## 1) Workflow Behavior

### ADR workflow sequence

Workflow: .github/workflows/adr-archunit-test-generation.yml

1. Collect ADR files.
2. Generate/update architecture and compliance tests with Copilot.
3. Run sync script.
4. Run sync script again (stability pass).
5. On pull_request, fail if tests changed in CI but were not committed.
6. Run coverage verification.
7. Run npm test.
8. On push event, optionally open/update generated-test PR.

### Why sync runs twice

The second sync pass eliminates order/timing drift after generation before verification executes.

### Node CI interaction model

Workflow: .github/workflows/node.js.yml

1. Ignores pure docs/decisions-only changes at trigger level.
2. Detects docs/decisions changes in mixed commits and skips build job.
3. Runs build/sync/verify/test only when docs/decisions is not part of the effective change set.

## 2) Marker Storage And Sync Contract

There is no standalone marker file.

Markers are inline comments inside test files.

Required marker:

- ADR_CONSTRAINT: <exact ADR bullet text>

Optional trace marker:

- ADR_MAPPING_RULE: <rule id>

### Where markers are written

1. scripts/sync-adr-constraint-tests.mjs
   - Each template renderer emits ADR_CONSTRAINT and ADR_MAPPING_RULE comments.
   - writeComplianceFile composes the full generated compliance file content.

2. Copilot generation step in ADR workflow
   - Prompt requires ADR_CONSTRAINT markers in architecture and compliance files.

### Where markers are verified

1. scripts/verify-adr-constraint-coverage.mjs
   - parseMarkers extracts ADR_CONSTRAINT entries from test files.
   - Expected marker sets are rebuilt from ADR constraints + mapping rules.
   - Compares expected vs actual for both architecture and compliance targets.

### Verification outcomes

1. Missing marker in expected file: fail.
2. Truly stale marker (constraint removed/remapped and expected in neither file): fail.
3. Misplaced duplicate marker (present but in wrong file while expected exists elsewhere): warning.

This marker comparison is the core keep-in-sync facility.

## 3) Constraint Routing Model

Rules are evaluated with first-match-wins semantics.

Each matched constraint resolves to one of two test types:

1. archunit
   - Expected marker location: tests/<decision>.test.ts

2. compliance-generated
   - Expected marker location: tests/<decision>.compliance.test.ts

Mapping source precedence:

1. ADR_CONSTRAINT_MAPPING_JSON environment variable.
2. Local fallback: docs/testing/adr-constraint-to-test-mapping.md.

## 4) Supported Constraint Template Tests

Implemented in scripts/sync-adr-constraint-tests.mjs.

### Deterministic enforcement templates

1. prefix-literal-ban
   - Extracts prohibited quoted prefix literal from constraint text.
   - Scans source for string literals beginning with that prefix.
   - Fails when prohibited literals are present.

2. id-prefix-ban
   - Enforces that id-like fields are not prefixed with literal text.
   - Detects literal concatenation and template-literal prefix patterns.

3. inheritance-depth-cap
   - Builds extends graph from classes.
   - Computes inheritance depth with cycle detection.
   - Fails when depth exceeds configured maxDepth.

4. literal-ban
   - Bans a configured literal (templateArgs.literal) across source corpus.

### Evidence templates

These assert implementation evidence terms exist in relevant source corpus.
They include a bootstrap guard: if target component roots do not exist yet, test passes as no-op.

1. sequence-evidence
   - Looks for sequence/order/replay/determinism evidence.

2. validation-evidence
   - Looks for validate/reject/invalid/auth/session-state style evidence.

3. quantity-lifecycle-evidence
   - Looks for quantity, partial fill, lifecycle, idempotency, at-most-once evidence.

4. metrics-ops-evidence
   - Looks for metrics/latency/archive/retention/failover/backpressure evidence.

5. security-privacy-evidence
   - Looks for auth/encrypt/entitlement/confidential/privacy evidence.

6. general-evidence
   - Catch-all executable evidence test.
   - Uses constrained term extraction to avoid generic false-positive terms.
   - Intended as a fallback only when a constraint does not yet have a dedicated test mapping.

### Legacy placeholder template

1. todo-constraint
   - Emits it.todo marker placeholder.
   - Supported for legacy mappings only; not preferred for new catch-all use.

## 5) Operations

### Standard local maintenance commands

```bash
ADR_FILES="$(printf '%s\n' docs/decisions/*.md)" node scripts/sync-adr-constraint-tests.mjs
ADR_FILES="$(printf '%s\n' docs/decisions/*.md)" node scripts/verify-adr-constraint-coverage.mjs
npm test
```

### CI policy behavior on ADR changes

1. ADR workflow regenerates + syncs + verifies.
2. On pull_request, if sync changed tests but commit did not include those updates, CI fails with a clear message.
3. This prevents merging ADR changes with stale generated test files.
4. If a constraint matches only the catch-all rule, the workflow surfaces it as a constraint that needs dedicated test mapping.
5. Optional strict mode: set ADR_FAIL_ON_BOOTSTRAP_MAPPING=true to fail CI whenever any constraint still relies on the catch-all rule.

## 6) Organization Portability

### Shared mapping strategy

Preferred:

1. Set organization Actions variable ADR_CONSTRAINT_MAPPING_JSON.
2. Keep local mapping file as fallback and local extension point.

### Minimal shared JSON shape

```json
{
  "rules": [
    {
      "id": "archunit-example",
      "pattern": "shall not import",
      "testType": "archunit"
    },
    {
      "id": "compliance-example",
      "pattern": "inheritance depth",
      "testType": "compliance-generated",
      "template": "inheritance-depth-cap",
      "templateArgs": {
        "maxDepth": 3
      }
    },
    {
      "id": "bootstrap-catch-all",
      "pattern": ".+",
      "testType": "compliance-generated",
      "template": "general-evidence"
    }
  ]
}
```

## 7) Troubleshooting

1. Coverage mismatch: stale marker
   - Meaning: ADR removed/remapped constraint, but old marker still exists in tests.
   - Action: run sync and commit updated generated test file.

2. Coverage mismatch: missing marker
   - Meaning: mapping expects a test marker that is absent.
   - Action: regenerate tests; verify mapping rule and destination test type.

3. Unmapped constraints in logs
   - Meaning: no mapping rule matched the constraint text.
   - Action: add or refine mapping rule; avoid over-broad patterns.

4. Constraint needs dedicated test mapping
   - Meaning: the constraint matched the catch-all rule instead of a dedicated mapping/template.
   - Action: add a precise mapping rule and, when needed, a dedicated template implementation.

5. PR fails with "ADR-derived tests are out of date"
   - Meaning: CI sync produced diffs under tests.
   - Action: run sync locally and include generated test diffs in commit.

## Recommended Policy

1. Keep mapped coverage strict and failing on drift.
2. Keep catch-all executable (general-evidence) instead of defaulting to todo placeholders.
3. Treat mapping edits as compliance-control changes requiring review.
